# 10. 프론트엔드 개발 가이드 — 브랜치 전략 · 개발 순서 · 전역 설정

> 이 문서는 **VS Code의 Claude Code가 실제 구현 작업을 할 때 참고하는 실행 가이드**입니다. 00~09번 문서(API/기능명세 정리)가 "무엇을 만들지"를 다뤘다면, 이 문서는 "어떤 순서로, 어떤 브랜치 구조로, 어떤 전역 규칙 위에서" 만들지를 다룹니다.

## 1. 브랜치 전략 — GitHub Flow (권장)

### 결론

**Git Flow가 아니라 GitHub Flow를 권장합니다.**

| 판단 근거 | 설명 |
|---|---|
| 배포 대상이 단일 | 이 프로젝트는 여러 버전을 동시에 유지보수하는 제품이 아니라, 정해진 대회 일자에 배포되는 **단일 웹앱**입니다. Git Flow의 `develop`/`release/*`/`hotfix/*`는 "여러 배포 버전을 동시에 관리"할 때 필요한데, 여기엔 그 필요가 없습니다.
| 일정이 짧고 고정 | 대회 날짜라는 하드 데드라인이 있는 단기 프로젝트라 브랜치 전환·머지 절차가 무거우면 오히려 속도가 떨어집니다.
| 페이지/컴포넌트 단위 병렬 작업이 핵심 요구 | 필요한 건 "여러 페이지를 여러 사람이 동시에, 짧은 주기로 `main`에 합치는 것"이지 "릴리즈 라인 관리"가 아닙니다. GitHub Flow(`main` + 짧은 수명의 feature 브랜치 + PR)가 정확히 이 요구에 맞습니다.
| `main`은 항상 배포 가능 상태 유지 | GitHub Flow의 핵심 규칙 — `main`에 머지된 것은 언제든 배포 가능해야 합니다. 대회 직전 급한 수정이 필요할 때도 별도 hotfix 절차 없이 바로 `main`에서 브랜치 파서 고치고 PR로 합치면 됩니다.

### 예외 — 대형 페이지는 "통합 브랜치"를 하나 더 둔다

보드 페이지(14개 API)와 관리자 페이지(12개 API)처럼 한 페이지 안에 컴포넌트가 많은 경우, 여러 사람이 그 페이지의 하위 컴포넌트를 동시에 작업할 수 있습니다. 이때는 Git Flow 전체를 도입하지 않고, **그 페이지 전용 통합 브랜치**만 하나 추가로 둡니다.

```
main
 └─ feature/board                      (보드 페이지 통합 브랜치)
     ├─ feature/board/dice             (주사위 컴포넌트)
     ├─ feature/board/chance           (찬스카드 컴포넌트)
     └─ feature/board/cell-open        (칸 오픈/문제선택 컴포넌트)
```

- 컴포넌트 브랜치는 `feature/board`에서 분기해 `feature/board`로만 머지합니다(`main`으로 직접 머지 금지).
- `feature/board`가 페이지 단위로 완성되면 그때 `main`으로 PR을 올립니다.
- 소규모 페이지(로그인/타이머/랭킹/리더보드/KOTH 등)는 이 단계 없이 `feature/<page>` 하나로 충분합니다.

## 2. 브랜치 네이밍 규칙

```
main                        # 항상 배포 가능한 상태
feature/<page-slug>         # 페이지 단위 기본 브랜치
feature/<page-slug>/<part>  # (대형 페이지에 한해) 컴포넌트 단위 하위 브랜치
fix/<slug>                  # 버그 수정
chore/<slug>                # 설정, 빌드, 문서 등 기능 외 작업
```

| 페이지(기능명세 기준) | slug | 담당(기능명세 명시) | 문서 |
|---|---|---|---|
| 로그인 페이지(인증) | `auth` | 준하 | `01_로그인페이지_인증.md` |
| 문제 리스트(보드) 페이지 | `board` | 지원 | `02_보드페이지.md` |
| 문제 상세 페이지 | `challenge-detail` | 규민 | `03_문제상세페이지.md` |
| 열린 문제 목록 페이지 | `open-challenges` | 규민 | *(이번 세션 문서화 범위 제외 — 사용자 요청)* |
| 리더보드 페이지 | `leaderboard` | 가연 | `04_리더보드페이지.md` |
| 랭킹 페이지 | `ranking` | 가연 | `05_랭킹페이지.md` |
| 마이 페이지 | `mypage` | 준하 | `06_마이페이지.md` |
| 타이머 페이지 | `timer` | 가연 | `07_타이머페이지.md` |
| 관리자 페이지 | `admin` | 준하 | `08_관리자페이지.md` |
| KOTH 페이지 | `koth` | 지원 | `09_KOTH페이지.md` |
| (페이지 아님) 공통 인프라 | `infra` 또는 `common` | — | 이 문서 3절 |

예: `feature/auth`, `feature/board`, `feature/board/dice`, `feature/admin`, `fix/ranking-team-name`.

## 3. 개발 순서 (의존성 + 백엔드 상태 기준 권장안)

```
Phase 0 — 공통 인프라 (전부 선행 필요, 다른 모든 브랜치가 여기서 분기)
  feature/infra
    - API 클라이언트(axios 인스턴스) + baseURL 전역 변수화
    - Authorization: Bearer 인터셉터 + 401 처리(재발급/로그아웃)
    - 라우팅 스켈레톤, 전역 레이아웃/스타일
    - KST 변환 유틸

Phase 1 — 인증 (Phase 0 다음 최우선, 다른 모든 페이지가 로그인 의존)
  feature/auth

Phase 2 — 핵심 게임 플로우 (병렬 가능, 서로 약하게 의존)
  feature/board
  feature/challenge-detail   (board에서 칸 오픈 → 문제 상세로 연결)
  feature/mypage             (팀 상태를 상시 참조하는 화면이라 일찍 필요)

Phase 3 — 조회 전용 페이지 (Phase 2와 병렬 가능, 서로 독립적)
  feature/leaderboard
  feature/ranking
  feature/timer
  feature/open-challenges

Phase 4 — 운영/부가 기능 (백엔드 상태가 대부분 "시작 전"/"논의"라 자연히 후순위)
  feature/admin
  feature/koth
```

- 담당자 매핑(기능명세 원문 "1. 로그인-마이페이지-어드민(준하) / 2. 리더보드-랭킹-타이머(가연) / 3. 보드-KOTH(지원) / 4. 문제상세-열린문제목록(규민)")과 맞춰보면, 담당자별로 Phase 0/1을 함께 끝낸 뒤 각자 자기 담당 페이지들을 순서대로 진행하는 방식이 자연스럽습니다.
- `admin`/`koth`는 API 자체가 "시작 전"/"논의" 상태가 많아(08/09번 문서 참고) 백엔드 확정을 마냥 기다리기보다 **목업 데이터로 UI를 먼저 만들고 나중에 연동**하는 순서를 권장합니다(08번 문서 8절, 09번 문서 8절 참고).

## 4. PR / 커밋 규칙

- **모든 변경은 PR을 통해서만 `main`(대형 페이지는 `feature/<page>`)에 들어간다.** 직접 push 금지.
- 커밋 메시지: `<type>(<scope>): <설명>` (Conventional Commits 스타일)
  - `type`: `feat`/`fix`/`refactor`/`style`/`chore`/`docs`
  - `scope`: 2절의 slug (예: `feat(board): 주사위 굴리기 API 연동`)
- PR 제목도 동일 규칙, 본문에 관련 문서(`0X_*.md`) 링크와 QA 체크포인트 반영 여부 명시.
- 머지 방식: **Squash merge** 권장(컴포넌트 단위의 자잘한 커밋이 `main` 히스토리를 어지럽히지 않도록).
- 머지 후 브랜치는 즉시 삭제.

### ⚠️ 커밋 작성자(Authorship) 규칙 — 반드시 준수

> **어떤 커밋에도 AI(Claude)가 기여자로 들어가면 안 됩니다.** `Co-Authored-By: Claude ...`, `Authored-By: Claude ...` 같은 trailer를 커밋 메시지에 절대 포함하지 마세요. 커밋 author/committer는 항상 실제 작업자(팀원) 계정이어야 합니다. Claude Code가 커밋을 생성/제안할 때도 이 규칙을 그대로 따라야 합니다.

## 5. 전역 설정 체크리스트 (모든 페이지 브랜치 공통 적용)

이 항목들은 사용자가 React 컴포넌트화 단계에서 명시적으로 요구한 사항입니다. 페이지별 브랜치에서 개별로 만들지 말고 **Phase 0(`feature/infra`)에서 한 번만 만들어 전체가 재사용**합니다.

### 5-1. Base URL — 전역 변수, 하드코딩 금지

```env
# .env
VITE_API_BASE_URL=http://msgctf.kr
VITE_API_PREFIX=/api/v1
```

```ts
// src/lib/apiClient.ts
import axios from "axios";

const baseURL = `${import.meta.env.VITE_API_BASE_URL}${import.meta.env.VITE_API_PREFIX}`;
// 예: http://msgctf.kr/api/v1
// 관리자 API 호출 시엔 baseURL + "/admin/..." 형태로 이어붙임(별도 baseURL 분리 불필요 — 08번 문서 API가 전부 /api/v1/admin 하위)

export const api = axios.create({ baseURL });
```

- 코드 어디에서도 `"http://msgctf.kr/..."`를 문자열로 직접 쓰지 않는다 — 전부 `api.get("/board")`처럼 `apiClient` 경유.

### 5-2. 인증 — Bearer 토큰 전역 인터셉터

사용자가 제시한 패턴을 인터셉터로 일반화합니다.

```ts
// src/lib/apiClient.ts (이어서)
api.interceptors.request.use((config) => {
  const token = getAccessToken(); // 인증 필요 없는 API(01/07/09번 문서의 인증불필요 목록)는 토큰 없어도 무방
  if (token) {
    config.headers.Authorization = `Bearer ${token}`;
  }
  config.headers["Content-Type"] = "application/json";
  return config;
});

api.interceptors.response.use(
  (res) => res,
  async (error) => {
    if (error.response?.data?.code === "TOKEN_EXPIRED") {
      // POST /auth/refresh(01번 문서)로 재발급 후 원 요청 재시도
    }
    return Promise.reject(error);
  }
);
```

- 인증 불필요 API 목록(요약): `GET /board`, `GET /board/chance/catalog`, `GET /leaderboard`, `GET /timer`, `GET /koth/clubs`, `GET /koth/clubs/{club_id}`. 그 외 대부분은 Bearer 필요.
- 응답 판정은 **HTTP 상태코드가 아니라 `code === "SUCCESS"` 여부**로 한다(공통 규약 — 00번 문서 참고). 예: 무인도 탈출 실패는 HTTP 200이지만 `code: "ESCAPE_FAILED"`.

### 5-3. KST 시간 — 전역 변환 유틸

모든 API 응답의 시간 필드는 **ISO-8601 UTC**(`Z` 접미사)로 내려옵니다. 화면 표시는 항상 KST로 변환합니다.

```ts
// src/lib/time.ts
export function toKst(isoUtc: string | null): Date | null {
  if (!isoUtc) return null;
  return new Date(isoUtc); // Date 객체는 내부적으로 UTC 저장 — 포맷팅 시 timeZone 지정
}

export function formatKst(isoUtc: string | null, pattern = "yyyy-MM-dd HH:mm:ss") {
  if (!isoUtc) return "-";
  return new Intl.DateTimeFormat("ko-KR", {
    timeZone: "Asia/Seoul",
    year: "numeric", month: "2-digit", day: "2-digit",
    hour: "2-digit", minute: "2-digit", second: "2-digit",
  }).format(new Date(isoUtc));
}
```

- 카운트다운(타이머/보드 주사위 리셋/문제 풀이 제한시간)은 `server_time`(내려주는 API에 한해)을 기준으로 클라이언트 시계 오차를 보정 — 02/07번 문서 참고. `server_time`이 없는 `GET /timer`는 07번 문서 7절의 미해결 이슈이므로, 연동 시 재확인 필요.

### 5-4. 상대 경로 — 문자열 하드코딩 대신 라우트 상수/헬퍼

```ts
// src/routes.ts
export const ROUTES = {
  board: "/board",
  challengeDetail: (id: string) => `/challenges/${id}`,
  kothClub: (kothChallengeId: string) => `/koth/leaderboard/${kothChallengeId}`,
} as const;

// 사용 예 (❌ 금지: navigate("./page/1"))
navigate(ROUTES.challengeDetail(challengeId));
```

- `react-router`의 `<Link to={...}>`/`navigate()`에 리터럴 문자열 대신 항상 `ROUTES` 헬퍼를 통해 경로를 만든다.
- 페이지네이션 등 쿼리스트링도 `URLSearchParams`로 조립하고 `?page=${n}` 같은 수동 문자열 조합을 지양한다.

### 5-5. Swagger/Postman 예시

- 00~09번 문서의 "3. 상세 명세" 코드블록(Request/Response/Error)이 그대로 Swagger(OpenAPI) `example`/Postman Collection의 소스가 됩니다. Phase 0에서 `apiClient` 완성 후, 문서의 JSON 예시를 Postman Collection으로 옮기는 작업을 별도 `chore/postman-collection` 브랜치로 진행 권장(페이지 개발과 병렬 가능).

## 5-6. Phase 0 스캐폴드 (구현 완료, 별도 파일 제공)

5절의 API 클라이언트/KST 유틸/라우트 헬퍼/인증 컨텍스트/라우트 가드를 실제 동작하는 Vite+React+TypeScript 프로젝트로 구현해뒀습니다(`msgctf-frontend-scaffold.zip`). `npm install && npm run build`까지 검증 완료. 이 스캐폴드를 팀 저장소에 `feature/infra`로 올리고 각 페이지 브랜치가 여기서 분기하면 됩니다. 구성/사용법은 스캐폴드 내 `README.md` 참고. 로그인/타이머/리더보드 3개 페이지는 실제 API 연동까지 데모로 구현되어 있고 나머지 6개(보드/문제상세/랭킹/마이페이지/관리자/KOTH)는 컴포넌트 분해 주석이 달린 스텁 상태입니다.

## 6. 페이지 브랜치 완료 기준 (Definition of Done)

각 `feature/<page>` PR을 `main`에 올리기 전 체크:

- [ ] `apiClient`(5-2) 경유로만 API 호출 — `fetch`/`axios` 직접 호출·baseURL 하드코딩 없음
- [ ] 인증 필요 API에 Bearer 헤더가 인터셉터를 통해 자동으로 실림
- [ ] 화면에 노출되는 모든 시간 필드가 KST로 변환되어 표시됨
- [ ] 페이지 내비게이션이 `ROUTES` 헬퍼 경유(상대경로 문자열 하드코딩 없음)
- [ ] 응답 성공 판정이 `code === "SUCCESS"` 기준(HTTP 상태코드만으로 판단하지 않음)
- [ ] 해당 페이지 문서(`0X_*.md`)의 "QA 체크포인트" 항목 확인 완료 또는 담당자 확인 대기 중임을 PR에 명시
- [ ] 커밋에 AI 공동저자 trailer 없음(4절)
